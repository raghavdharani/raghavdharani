## How I work

| Principle | In practice |
|---|---|
| Start with the operating reality | I spend time with the people doing the work, map exceptions early, and design for the conditions that exist rather than the happy path. |
| Make decisions inspectable | Clear problem framing, explicit trade-offs, and written product decisions keep teams aligned when the answer is not obvious. |
| Prototype before the handoff | I use working prototypes and detailed specs to test workflows with stakeholders before engineering commits to the build. This has reduced clarification cycles by about 25% and rework by 20 to 30%. |
| Treat adoption as a product problem | A launch is useful only when behavior changes. Rollout design, feedback loops, and operational measures are part of the product itself. |
| Use AI where it improves judgment | I am interested in AI that structures messy inputs, surfaces blind spots, and helps people make decisions they can explain. |
